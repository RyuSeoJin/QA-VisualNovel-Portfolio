# sut-automation — SUT 제작·자동화 공통 규칙

테스트 대상(SUT)을 직접 만드는 프로젝트가 따르는 방법론 정본입니다. 여기는 프로젝트와
무관한 **원칙**만 두고, 실물(이 SUT의 testid 목록·API·화면)은 각 프로젝트의
`spec/sut-design/{프로젝트}-sut-blueprint.md`가 정본입니다.

규칙을 적용하다 빈틈이 발견되면 임의로 고치지 않고 제안 → 승인 → change-log 기록의
개정 절차를 따릅니다.

---

## 1. SUT 제작 규칙

**SUT 테스트 인터페이스** — SUT가 테스트 코드에 공식적으로 열어주는 접점 — 를 구현
시작 시점부터 심습니다. 완성 후에 붙이면 셀렉터와 상태 구조가 이미 굳은 코드에 맞춰
뒤틀리므로, 사후 부착을 금지합니다. 갈래는 아래 표와 같고, 프로젝트가 실제로 갖는 갈래
구성의 정본은 그 프로젝트의 청사진입니다.

| 갈래 | 규칙 | 이유 |
|---|---|---|
| 요소 셀렉터 | 테스트는 요소를 `data-testid`로만 찾습니다. CSS 클래스·화면 문구로 찾는 것은 금지 | 문구·디자인이 바뀌어도 테스트가 살아남아야 합니다 |
| 상태 조회·제어 API | 전역 객체로 내부 상태의 읽기 전용 사본을 노출하고, 초기화(`reset`)를 반드시 제공합니다 | 격리 계열 검증(슬롯 오염·삭제 기억 재등장·계정 잔존)은 화면에 나타나지 않아 **이 통로가 유일한 검증 수단**입니다 |
| 실행 조건 파라미터 | mock 응답은 시드 파라미터로 결정적으로 고정하고, 결함 주입 스위치를 파라미터로 둡니다 | 시드는 실패 재현을, 주입은 테스트 탐지력 증명(§5)을 가능하게 합니다 |
| 데이터 주입 | 목록·집계·표시가 읽는 조건 데이터는 전역 객체의 주입 API로 넣습니다. 사람용 편집 UI를 함께 두는 경우 두 경로는 같은 저장소를 씁니다 | 화면 조작만으로 경계 조건(최대 개수·중복·빈 상태)을 만들면 세팅 비용이 테스트마다 커지고 조건 재현이 셀렉터 경로에 묶입니다. 저장소가 갈리면 사람 검증과 자동화의 재현이 어긋납니다 |

- `data-testid` 명명 규칙은 SUT 코드 첫 줄을 쓰기 **전에** 청사진에서 확정합니다 —
  뒤로 미루면 셀렉터가 깨지며 자동화 하루가 사라집니다
- 결함 주입의 종별·주입 지점·기대 탐지 TC는 프로젝트의 fault-injection 명세가 정본입니다
- SUT는 문서가 아니라 프로그램이므로 자기완결 단일 파일 규칙의 예외입니다(CLAUDE.md).
  코드와 청사진이 어긋나면 청사진을 먼저 고칩니다

## 2. 자동화 케이스 규칙

- **케이스명 = TC ID** — `test_tc_{영역코드}_{번호}_{요약}` 형식으로, 리포트만 보고 TC
  시트와 대조되게 합니다
- 테스트 파일은 기능 트리 1-Depth 영역 단위로 나눕니다 — TC ID의 영역코드와 파일이
  대응됩니다
- **매 테스트 전 `reset()`** 을 공용 픽스처(conftest)에서 강제합니다 — 앞 테스트의
  상태가 남으면 격리 검증 자체가 무의미해집니다
- **반복은 테스트 함수 안에서** 돌립니다. parametrize로 쪼개면 반복이 독립 케이스로
  집계되어 성공률을 계산할 수 없으므로 금지합니다
- 검증유형별 작성법:

| 유형 | 작성법 |
|---|---|
| 결정적 | 1회 실행, 기대값 불일치 시 FAIL |
| 금칙 | 정의된 시도 목록을 전부 실행, 하나라도 통과(차단 실패)하면 FAIL |
| 확률적 | 함수 안에서 N회 반복, 성공률 ≥ 임계면 PASS — 계측임을 케이스 docstring에 명시 |
| 루브릭 | **자동화하지 않습니다.** 채점은 §4의 수동 결과 통합으로 |

- 실행 상태는 4종(Pass/Fail/NI/Blocked, 정의는 `tc-sheet-format.md`)과 대응시킵니다 —
  SUT 미구현(보류) 노드의 TC는 NI, 선행 실패로 막힌 것은 Blocked
- 자동화는 xlsx가 아니라 **TC 설계 원본(tc-input json)을 읽습니다** — 커버리지 대조와
  검증유형별 반복 횟수 결정이 목적이며, xlsx는 사람용 파생물입니다

## 3. 임계·반복 관리

- 반복 횟수·합격선·시도 목록 크기는 **thresholds 모듈 한 곳**에 모읍니다 — 케이스마다
  흩어지면 리포트의 수치와 코드의 실제 값이 어긋나기 시작합니다
- 리포트는 이 모듈의 값을 읽어 표기합니다. 리포트에 수치를 하드코딩하지 않습니다
- 임계값 변경은 스펙 변경입니다 — 커밋 [스펙 변경]과 change-log에 기록합니다

## 4. 수동 결과 통합

- 루브릭 채점은 사람이 수행하고 결과를 `rubric-scores.csv`로 남깁니다 — 최소 컬럼:
  TC ID · 평가 기준 · 점수 · 만점 · 비고. 기준과 합격선의 정본은 프로젝트의 루브릭 정의서
- 리포트가 이 CSV를 읽어 자동 결과와 **한 리포트에서** 집계합니다 — 수동 결과가 별도
  문서로 떠돌면 커버리지가 이중 장부가 됩니다

## 5. 리포트 규칙

- **검증유형별로 집계를 분리**합니다 — 완전 검증(결정적·금칙 격리)과 계측(확률적·루브릭)을
  한 평균으로 섞으면 수치의 의미가 사라집니다
- **결함 주입 매트릭스를 포함**합니다 — 행=주입 결함, 열=담당 TC. **대각선만 FAIL이
  정상**이며, 대각선이 PASS면 그 TC가 결함을 못 잡는다는 뜻이므로 케이스로 되돌아갑니다
- 분석·리포트에는 **"SUT 한계와 검증 범위" 섹션을 필수**로 둡니다 — 정본 소스는 청사진의
  검증 가능성 맵이며, 계측 수치를 품질 지표로 서술하지 않습니다
- 리포트·결과 시트는 파생물입니다 — 직접 수정하지 않고 재생성만 합니다

## 6. CI 규칙

- **`deploy-pages` 액션을 쓰지 않습니다** — Pages 배포 방식을 브랜치 배포에서 Actions
  배포로 바꾸면 기존 사이트가 내려갑니다. 리포트는 저장소에 커밋해 Pages가 서빙합니다
- 리포트는 `upload-artifact`로도 남깁니다(기본 90일 만료) — 커밋본은 대표 1부만 두고,
  CI 실행분을 전부 커밋하면 이력이 결과 파일로 도배되므로 나머지는 artifact로 흘립니다
- 경로 필터로 필요할 때만 실행합니다 — SUT·자동화·TC 입력이 바뀔 때
- 결함 주입 매트릭스를 CI에 묶어, 탐지력 검증이 사람 손 없이 반복되게 합니다
