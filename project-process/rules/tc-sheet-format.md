# TC 시트 서식

## 원칙: 기존 서식이 있으면 그 서식을 쓴다

**새 레이아웃을 발명하지 마세요.** 조직에 이미 쓰는 TC 시트가 있으면 컬럼 구성·문체·상단
블록을 그대로 따릅니다. 없을 때만 아래 표준 서식으로 만듭니다. 서식을 확인하지 않고 임의
레이아웃을 만드는 것은 이 스킬에서 가장 흔한 실수입니다 — 반드시 먼저 물어보거나 기존 파일을
읽으세요.

---

## 표준 서식 (기본값)

한 행이 곧 한 스텝입니다. 상단에 테스트 환경 블록, 그 아래 데이터 행이 이어집니다.

### 컬럼

| 컬럼 | 내용 | 채우는 규칙 |
|---|---|---|
| No | 행 번호 | 자동 (`=ROW()-기준`) |
| 1-Depth ~ 7-Depth | 기능 계층 | 스텝 행마다 반복. 의미 있는 깊이까지만, 나머지는 빈칸 |
| Pre-Condition | 사전조건 | **TN 1행에만** |
| TN | 스텝 번호 | 케이스마다 1부터. → `depth-and-tn.md` |
| Test-Step | 수행 동작 | `~한다` 체 |
| Expected-Result | 기대 결과 | `~된다` 체. 판정 가능한 문장 |
| Priority | 우선순위 | **TN 1행에만**. High/Medium/Low |
| Total Result | 케이스 판정 | 플랫폼별(예: Web/And/iOS). Result 행을 훑는 수식 |
| Result | 스텝 실행 결과 | 플랫폼별. Pass/Fail/Blocked/N/A/Skip 드롭다운 |
| JIRA No. | 이슈 링크 | 실행 시 입력 |
| Comment | 메타 | TC ID · 실행 단계 · 선행 TC · 대상. → `tc-relations.md` |
| Note | 검증 정보 | 검증유형과 판정 규칙, 주의사항 |
| Test Case Edit | 편집 이력 | 자유 |

### 상단 환경 블록

데이터 행 위에 OS / 단말 / 버전 / 작업자 이름 / 작업 시작일을 플랫폼 열마다 적는 칸을 둡니다.
실행자가 어떤 환경에서 돌렸는지가 결과 해석의 전제입니다.

### 입력 셀 구분

실행자가 채우는 칸(환경 정보 / Result / JIRA No. / Comment)은 배경색(노란색 등)으로 구분해,
설계 산출물(Depth·절차·기대결과)과 시각적으로 분리합니다. 설계 칸은 실행 중 건드리지 않습니다.

## 한 행 = 한 TN = 한 스텝

핵심 규칙입니다. 케이스 하나가 스텝 여러 개면 행 여러 개로 펼쳐집니다.

```
No  1-Depth  2-Depth       Pre-Condition           TN  Test-Step           Expected-Result       Priority
5   앱 진입   최초 실행       로그인 후 세션 만료         1   앱 실행한다           앱이 정상 기동된다      High
6   앱 진입   최초 실행                                2   노출 화면 확인한다     로그인 화면 노출된다
7   앱 진입   최초 실행                                3   재로그인 수행한다      재로그인 성공한다
8   앱 진입   최초 실행                                4   복귀 화면 확인한다     만료 직전 화면으로 복귀된다
```

- Depth는 **스텝 행마다 반복**해서 적습니다.
- Pre-Condition·Priority는 **TN 1행에만**. 우선순위는 스텝이 아니라 케이스의 속성입니다.
- 기대 결과가 한 스텝에 여러 개면 **같은 TN을 유지한 채 행을 늘리고** No·Depth·Test-Step은 비웁니다.
- 새 케이스가 시작되면 TN이 다시 1로 돌아갑니다.

## 문체

| | 형식 | 예 |
|---|---|---|
| Test-Step | `[대상] [동작]한다` | 좌측 상단 영역 확인한다 / 집중 버튼 선택한다 / 앱 실행한다 |
| Expected-Result | `[대상] [상태]된다` | 스테이터스 패널 노출된다 / 재화가 차감된다 / 연인 단계로 전이된다 |

기대 결과는 **판정 가능**해야 합니다. "정상 동작한다"는 기대 결과가 아닙니다. 확률적 TC는
임계값을, 루브릭 TC는 합격선을, 금칙 TC는 시도 횟수를 문장 안에 숫자로 적습니다.
→ 판정 규칙은 `verification-types.md`.

## Total Result 수식

케이스의 여러 스텝 Result를 하나로 요약합니다. Fail 우선, 다음 Blocked, 다음 Pass.

```
=IF(COUNTIF(Result범위,"Fail")>0,"Fail",
 IF(COUNTIF(Result범위,"Blocked")>0,"Blocked",
 IF(COUNTIF(Result범위,"Pass")>0,"Pass","")))
```

플랫폼 열이 여러 개면(Web/And/iOS) 각 열마다 별도로 요약합니다. 웹 클라이언트가 없는 앱 전용
서비스면 그 열은 두되 N/A로 채우거나, 대상 서비스에 맞게 열 자체를 줄입니다.

## 커버리지 집계

별도 Summary 시트에서 영역별로 집계합니다. 수식으로 자동 계산되게 두어, 행을 추가해도 범위만
넓히면 갱신되도록 합니다.

- TC 수 = TN 1행의 개수 (케이스 단위)
- 테스트 스텝 = 전체 데이터 행 수 (스텝 단위)
- Pass율 = Pass / (Pass + Fail) — **Blocked는 분모에서 제외**. → `tc-relations.md`

Priority는 TN 1행에만 있으므로 우선순위 집계는 자연히 케이스 단위와 일치합니다.

## 생성 스크립트

`scripts/build_tc_template_xlsx.py`가 이 서식으로 시트를 만듭니다. 절차의 `1. / 2. / 3.`을
TN 스텝으로 자동 분해하고, `scripts/norm.py`가 문체를 `~한다` / `~된다`로 정규화합니다.

```bash
python scripts/build_tc_template_xlsx.py input.json -o 결과.xlsx
python /mnt/skills/public/xlsx/scripts/recalc.py 결과.xlsx   # 수식 검증 (필수)
```

**조직 서식이 표준과 다르면 스크립트를 그 서식에 맞게 고쳐 쓰거나, 생성 후 컬럼을 재배치합니다.**
스크립트의 서식이 조직 서식보다 우선하지 않습니다.
