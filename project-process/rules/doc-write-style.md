# doc-write-style — 문서 작성 규칙

이 워크스페이스에서 만드는 모든 문서의 문체와 문장 구조를 정합니다.
문서마다 말투와 설명 순서가 달라지면 읽는 사람이 매번 다시 적응해야 하므로, 기준을 한곳에 모읍니다.

---

## 1. 문체 — 경어체

문서 본문은 경어체(`~합니다` / `~입니다`)로 씁니다.

**예외는 명사로 끝나는 표현입니다.** 표의 항목, 제목, 목록의 짧은 라벨처럼 서술이 아닌 자리에서는
명사로 끝내도 됩니다 — 소개, 규칙, 문서, 확인, 정리, 진입점 같은 표현이 여기 해당합니다.

| | 예 |
|---|---|
| 경어체로 씁니다 | 골격이 확정되기 전에는 TC 설계로 넘어가지 않습니다. |
| 이렇게 쓰지 않습니다 | 골격이 확정되기 전에는 TC 설계로 넘어가지 않는다. |
| 명사로 끝내도 됩니다 | 저장소 소개 / 방법론·운영 규칙 정의 / 절차 확인 문서 |

---

## 2. 문장 구조 — 이유 → 작업 → 결과

**이유를 먼저 씁니다.** 변경 내용을 먼저 읽고 마지막에 이유를 알게 되면, 독자는 앞으로 되돌아가
문장을 다시 해석해야 합니다. 이유가 앞에 있으면 그 되감기가 사라집니다.

**지금까지의 방식**
> change-log를 이원화했습니다. 문서 이력은 작업 전 항상 읽는 파일, 골격 이력은 평소에 열지 않는
> 파일로 분리했습니다. 삭제·수정된 옛 기능 정보가 현재 작업에 섞여 들어오는 것을 막기 위해서입니다.

**이 규칙을 따른 방식**
> 삭제·수정된 옛 기능 정보가 현재 작업에 섞이지 않도록, 문서 이력과 골격 이력을 참조 규칙이
> 정반대인 두 파일로 분리했습니다. 그래서 평상시 작업에서는 골격 이력을 아예 열지 않습니다.

### 2-1. 문장이 길어진다고 판단되면 끊습니다

한 문장에 이유와 작업과 결과를 모두 욱여넣으면 주어와 서술어가 멀어져서 읽기 어려워집니다.
쓰는 도중에 길다고 느껴지면 문장을 끊습니다.

**끊는 지점은 길이가 아니라 의미의 경계에서 정합니다.** 길이는 "끊을지 검토하라"는 신호일 뿐이고,
어디서 끊을지는 내용이 결정합니다. 이유에서 작업으로 넘어가는 지점, 작업에서 결과로 넘어가는 지점,
또는 앞뒤의 논리 관계가 바뀌는 지점이 자연스러운 경계입니다.

수식어와 그 대상 사이, 조건절 중간, 나열의 도중처럼 **의미가 아직 닫히지 않은 자리에서는 끊지
않습니다.** 그 자리에서 끊으면 앞 문장이 미완성으로 남고 뒤 문장은 맥락을 잃습니다. 마땅한 경계가
없는데 문장이 길다면, 끊기 전에 먼저 문장을 다시 구성해 보고, 그래도 길면 길게 둡니다(2-3 참고).

### 2-2. 끊을 때 필요하다고 판단되면 접속사를 붙입니다

문장을 끊으면 앞뒤 관계가 흐려질 수 있습니다. 그럴 때는 접속사(왜냐하면, 그리고, 그래서, 하지만
등)로 연결해 두 문장이 어떤 관계인지 드러냅니다.

### 2-3. 정확성이 길이보다 우선입니다

**문장은 길어져도 됩니다.** 이유·작업·결과가 정확히 설명되지 않는다면 문장을 줄이지 않습니다.
짧게 만드느라 근거나 조건이 빠지면, 읽는 사람이 그것을 스스로 추측하게 되고 결국 잘못 이해합니다.

### 2-4. 말만 바꾼 반복을 피합니다

설명하는 과정에서 불가피한 경우는 있지만, 앞 문장을 표현만 바꿔 되풀이하지 않도록 유의합니다.
특히 결과를 적을 때 앞의 작업 문장을 다른 말로 옮기기 쉬우므로 주의합니다.

**피해야 하는 것은 같은 내용의 말바꿈이지, 결과 서술 자체가 아닙니다.** 결과가 독자의 판단이나
행동을 바꾸지 않더라도, 문맥상 마무리가 필요하면 씁니다. 결과 문장 없이 끝나 글이 끊긴 느낌이
든다면 그것도 읽기 불편한 글입니다.

다만 그럴 때는 앞 문장을 되풀이하지 말고 **새로운 정보를 담습니다.** 적용 범위, 조건, 예외,
이후 작업에 미치는 영향처럼 앞에서 말하지 않은 것을 적으면 반복이 아니라 확장이 됩니다.

## 3. 적용 예외

예외마다 면제되는 범위가 다릅니다. 어떤 것은 문장 구조만 예외이고, 어떤 것은 문체까지 예외입니다.

### 3-1. qa-doc-playbook.md — 문장 구조(2)만 예외

절차서는 "무엇을 하라"가 먼저 와야 손이 움직입니다. 이유를 앞세우면 지시가 뒤로 밀려 절차를
따라가기 어려워집니다. 이유가 필요하면 지시 뒤에 짧은 부연으로 붙입니다.

**문체(1)는 그대로 적용합니다.** 절차서도 경어체로 씁니다.

### 3-2. TC 시트의 문체 — 문체·구조 모두 예외

Test-Step은 `~한다`, Expected-Result는 `~된다`로 씁니다. 이것은 문서 서술이 아니라 시트 셀에
들어가는 **데이터의 표기 규약**이므로 경어체로 바꾸지 않습니다. 규정과 예시는
`tc-sheet-format.md`·`depth-and-tn.md`·`case-expansion.md`에 있습니다.

### 3-3. 코드 주석·독스트링·SVG 내부 주석 — 문체·구조 모두 예외

스크립트를 고칠 사람이 읽는 기술 메모이고, 형식 예시나 데이터 샘플이 섞여 있어 문체를 손대면
예시까지 바뀔 위험이 있습니다. 원문 그대로 둡니다.

### 3-4. 인용·원문 발췌 — 문체·구조 모두 예외

외부 문서나 대상 서비스의 문구를 옮겨 적을 때는 원문을 고치지 않습니다.

---

## 4. 적용 범위

문서 본문(md·html), 변경 이력(change-log), 커밋 메시지 본문의 서술 문장에 적용합니다.
커밋 메시지는 `qa-git-rules.md`가 이미 사유를 본문 첫 항목으로 두고 있으므로, 이 규칙의
"이유 → 작업 → 결과" 순서와 어긋나지 않습니다.
