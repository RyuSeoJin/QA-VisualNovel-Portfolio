# qa-git-rules — GitHub 커밋·push·브랜치 규칙

이 저장소의 모든 git 작업이 따르는 규칙입니다. 2026-07-31 확정했습니다.
Claude는 이 규칙 밖의 git 작업을 임의로 수행하지 않습니다.

## 1. 원칙

- **커밋·push는 사용자 요청 시에만 합니다.** Claude는 작업 단위가 끝나면 "커밋 시점"임을 제안만 하고, 실제 커밋은 사용자가 요청하고 내용을 승인했을 때만 수행합니다.
- **커밋과 push는 별개 승인입니다(분리형).** 커밋 승인이 push 승인을 포함하지 않습니다. 로컬에 커밋을 쌓아두고, 사용자가 push를 요청할 때만 공개합니다.
- **이 저장소는 public이므로 push가 곧 공개입니다.** 그래서 push 전에 저작권 게이트(§5)를 반드시 통과해야 합니다.

## 2. 커밋 단위

- 한 커밋은 한 작업 단위입니다. 골격 수정 1건, 문서 1건 생성, 규칙 1건 개정이 그 예입니다.
- **영역을 섞지 않습니다.** 프로젝트 작업과 규약(project-process) 수정, 디자인 시스템 갱신이 한 번에 발생했다면 영역별로 커밋을 나눕니다. 제목이 "정보 누락 없이"를 지키려면 커밋이 단일 영역이어야 하기 때문입니다.
- 예외로, 하나의 원인으로 여러 영역이 함께 바뀐 경우(예: Case B 마스터 갱신 + 그 마스터로 만든 문서)는 한 커밋으로 묶되 본문에 영역별로 나눠 적습니다.
- **원인이 다른 작업이 한 커밋에 들어가는 경우에도 본문에서 작업 단위를 나눠 적습니다.** 같은 흐름의 규칙 정비이거나, 한 파일이 여러 작업에 걸쳐 부분 스테이징 없이는 갈라지지 않을 때가 여기 해당합니다. 이때는 [작업 목록]의 항목을 작업 단위별로 묶고 무엇이 한 단위인지 드러나게 적습니다. 커밋 하나에 여러 결정이 들어 있어도 나중에 단위별로 복원되어야 하기 때문입니다.
- 다만 이 묶음은 편의를 위한 것이 아닙니다. 작업 단위가 서로 무관하고 파일도 겹치지 않는다면 커밋을 나눕니다.

## 3. 커밋 메시지 규격

한 화면에서 섹션이 구분되어 읽히도록, 대괄호 헤더와 빈 줄로 본문을 가릅니다(2026-08-01 개정).

```
[{영역}] {무엇을} {어떻게 했는지 — 정보 누락 없이}

[작업 목록]

* (작업 단위 1 — 이유→작업 순서로)
   * (다른 작업이 원인이 되어 파생된 것은 들여써서 인과를 드러낸다. 부모에 붙여 씀)

* (작업 단위 2 — 최상위 항목 사이는 빈 줄로 띄운다)

[스펙 변경]

* (수치·용어·규칙 변경 전부. 골격 버전 변화, 이전 산출물과 비호환이 되는 삭제,
   마스터/템플릿 갱신(Case B/C), 미확인(?) 증감, 이슈/TC 참조도 여기에 항목으로)

[변경 파일]

* (목록 요약)

[상세]

* {프로젝트}-change-log.md 또는 spec/archive/{프로젝트}-tree-change-log.md 해당 항목

[주의]

* (다음 작업자가 놓치기 쉬운 것 — 있을 때만)

Co-Authored-By: Claude {모델} <noreply@anthropic.com>
```

- `{영역}` = 프로젝트명(예: `demo-vn`) 또는 `process`(규약) · `design`(디자인 시스템) · `repo`(루트/구조).
- 해당 없는 섹션은 빈 채로 두지 않고 **통째로 생략합니다.** 본문에는 실제 정보만 남깁니다.
- **[작업 목록] 항목은 한 문장에 욱여넣지 않습니다.** 한 줄로 압축하면 인과가 사라져 나중에 왜 그렇게 했는지 복원할 수 없습니다. 여러 갈래의 이유가 있으면 갈래마다 항목을 나눠 적고, 앞선 작업 때문에 파생된 작업은 들여쓰기로 중첩해 "무엇 때문에 무엇을 하게 됐는지"가 읽히게 합니다.
- **[작업 목록] 항목은 이유 → 작업 → 결과 순서로 씁니다.** 문장 구조 규칙의 정본은 `doc-write-style.md` §2이며, 커밋 메시지 본문도 적용 범위입니다. 작업을 앞에 쓰고 이유를 뒤에 붙이면 나중에 이력을 되짚을 때 이유가 늦게 드러나 문장을 다시 해석해야 하므로, "무엇을 했다 — 왜냐하면"이 아니라 "무엇 때문에 무엇을 했다"로 적습니다.
- **change-log와의 역할 분담**: 상세 기록의 정본은 change-log입니다. 커밋 본문은 요약이며 `상세:` 줄로 change-log를 가리킵니다. 같은 내용을 양쪽에 전문으로 중복 기재하지 않습니다.
- Co-Authored-By 서명은 유지합니다(AI 협업 워크플로우 증빙). `{모델}` 자리에는 실제로 작업한 모델명을 적습니다 — 증빙이므로 템플릿에 특정 모델명을 박아두지 않습니다.
- **커밋 직전에 서명의 모델명을 매번 확인합니다.** 앞선 커밋 메시지를 그대로 베끼면 세션 중
  모델이 바뀌었을 때 서명이 조용히 틀어집니다(2026-08-02까지 두 차례 발생). 이력에 남는 증빙이
  실제와 다르면 협업 기록으로서의 값어치가 사라지므로, 직전 커밋을 참고하더라도 서명 줄만은
  현재 세션의 모델명으로 다시 적습니다.

## 4. 승인 플로우

1. 작업 완료 → Claude가 "커밋 시점 같습니다"라고 제안합니다.
2. 사용자가 커밋 요청 → Claude가 **① 제목 ② 본문 ③ 대상 브랜치** 3항목을 제시합니다.
3. 사용자가 승인 → 커밋을 수행합니다. 수정 지시가 있으면 반영 후 다시 제시합니다.
4. push는 별도입니다. 사용자가 push를 요청하면 저작권 게이트(§5) 통과를 확인한 뒤 push합니다.

## 5. push 전 저작권 게이트

push 대상 커밋에 역분석 자료가 포함되어 있으면 아래를 점검하고, 하나라도 걸리면 **push를 보류하고 사용자에게 보고합니다.**

- [ ] 대상 서비스의 스크린샷 포함 여부
- [ ] 게임/서비스 원문 텍스트 인용 포함 여부 (인용 시 최소 범위·출처 표기 확인)
- [ ] 상표·로고 노출 여부
- [ ] 비공개 자료(유출본·내부 문서) 포함 여부 — 발견 시 push 금지

역분석 자료의 저작권 점검은 push 시점만이 아니라 해당 자료를 처음 다루는 작업 시작 시점부터 수행합니다(qa-doc-playbook의 저작권 체크리스트 참조).

## 6. 브랜치 전략 (main 단일 · 2026-08-03 개정)

- **전부 `main`에 직커밋합니다.** 브랜치도 PR도 쓰지 않습니다.
- **왜 단일인가** — 지금은 완성된 제품의 빌드·릴리스를 관리하는 단계가 아니라 **하나의 프로젝트를
  처음부터 만들어 가는 과정**입니다. 산출물이 서로 물려 있어(트리를 고치면 명세·TC·SUT가 함께
  움직입니다) 갈래를 나누면 병합할 것이 아니라 맞물릴 것만 늘어납니다.
- **포트폴리오 증빙은 커밋 이력이 담습니다.** 개정 전에는 「과정 커밋이 PR에 보존되는 것」을
  증빙으로 삼았지만, 커밋 메시지가 §3 규격대로 이유→작업→결과를 항목으로 적고 있어 이력만으로도
  판단 과정이 읽힙니다. PR이라는 껍데기가 없어도 잃는 것이 없습니다.
- **다시 볼 조건** — 개발이 끝나고 릴리스 단위로 버전을 관리하게 되거나, 여러 사람이 같은
  저장소를 동시에 만지게 되면 그때 브랜치 전략을 다시 세웁니다. 그 전에는 나누지 않습니다.

> 개정 전에는 혼합형이었습니다 — 평상시 `main` 직커밋, 큰 산출물 셋(역분석/기획서 분석 문서
> 완성 · TC 세트 완성 · 골격 major 개정)만 `{프로젝트}/{산출물}` 브랜치를 파서 merge commit으로
> 병합. 실제로 브랜치를 판 적은 없으며, TC 세트 착수 시점에 단일로 확정했습니다.

## 7. 태그 (버전 좌표)

- 태그는 "완성 시점의 이정표"로만 씁니다. 커밋 이력이 작업 과정을 담고, 태그가 버전 좌표를 담습니다.
- 형식: 골격 major 개정은 `{프로젝트}-tree-v2.0`, TC 세트 완성은 `{프로젝트}-tc-v1.0`.
- annotated tag로 만들고, 메시지에 한 줄 요약을 담습니다.
- **archive/ 스냅샷 파일명의 버전과 태그 버전은 항상 일치시킵니다** (예: 태그 `demo-vn-tree-v1.0` ↔ `archive/demo-vn-feature-tree-v1.0.md`).

## 8. 기타

- 원격: GitHub public 저장소 `RyuSeoJin/QA-VisualNovel-Portfolio`.
- 되돌림이 필요하면 `git revert`(새 커밋으로 되돌리기)를 기본으로 합니다. 이력을 지우는 force push는 사용자의 명시 요청 없이 수행하지 않습니다.
