# 케이스 전개 규칙

기능 트리의 노드 하나를 TC 여러 건으로 펼치는 규칙입니다. 네 갈래를 순서대로 적용합니다.

## 1. 정상 (Happy path)

기능이 의도대로 쓰이는 경로. 노드당 최소 1건. 이것이 그 노드의 TN 앵커가 되는 경우가 많습니다.

## 2. 경계 (Boundary)

수치 제약이 있는 모든 곳에 **경계-1 / 경계 / 경계+1** 세 점을 찍습니다.

전개 대상이 되는 제약의 종류:

| 종류 | 예 |
|---|---|
| 글자수 | 이름 2~30자, 프롬프트 상한, 한 줄 소개 |
| 개수 | 스탯 7개, 키워드 노트 20개, 세이브 슬롯 100개, 예시 대화 3개 |
| 용량·수량 | 이미지 5MB, 1회 업로드 1,000장, 총 1,600장 |
| 금액·재화 | 결제 한도, 잔액 부족 직전, 무료 한도 소진 직전 |
| 시간 | 일일 리셋 시각, 유효기간 만료일, 만료 24시간 |
| 상태 임계 | 관계 단계 전이값, 엔딩 조건 턴수, 스탯 구간 경계 |
| 주기 | "10턴 이후 5턴마다" 같은 검사 주기 — 검사/미검사 턴 모두 확인 |

**등호 포함 여부를 반드시 확인합니다.** `>= 50`인지 `> 50`인지가 오프바이원 결함의 단골입니다.

**제약값을 모르면 경계 TC를 쓰지 말고 "상한 실측" TC를 씁니다.** 추측한 경계값으로 만든
TC는 전부 오탐이 됩니다.

## 3. 예외 (Exception)

정상 경로가 실패하는 상황. 다음 축을 기계적으로 훑습니다.

- **네트워크** — 단절, 저속, 타임아웃, 요청 중 백그라운드 전환
- **동시성** — 버튼 연타, 다중 기기 동시 조작, 재시도 중복
- **권한** — 알림·마이크·사진 권한 거부, 인증 만료, 구독 만료
- **입력 이상** — 빈 값, 공백만, 특수문자, 이모지, 매우 긴 입력, 예약어
- **자원 부족** — 잔액 0, 저장 공간 부족, 광고 재고 없음
- **서버 오류** — 5xx, 레이트리밋, 필터 차단, 모델 제공사 거부

예외 TC의 기대 결과에는 **"재화 미차감"과 "데이터 무손실"을 항상 명시**합니다.
실패 경로에서 돈이 빠지거나 데이터가 날아가는 것이 이 도메인의 대표 사고입니다.

## 4. 우회 (Bypass)

의도된 제약을 뚫으려는 시도. **금칙 검증유형은 대부분 여기서 나옵니다.**

- **경로 우회** — 검색으로 막혔으면 링크 직접 접근, 딥링크, 뒤로가기, API 직접 호출
- **상태 우회** — 인증 해제 후 기존 세션 재사용, 구독 만료 후 캐시된 화면
- **표현 우회** — 은유·완곡, 인코딩, 다국어, 오타·자모 분리
- **시간 우회** — 점진적 에스컬레이션(N턴에 걸쳐 서서히), 세션 재시작 후 재시도
- **주체 우회** — 캐릭터 프롬프트에 미리 심어두기, 유저노트에 넣기, 파일 업로드로 주입
- **어뷰징** — 다중 계정, 동일 기기 반복, 자기 콘텐츠 자기 소비로 지표 부풀리기

## SUT 특성에 따른 축 조정

위 축들은 **모든 프로젝트가 전부 훑어야 하는 목록이 아닙니다.** 테스트 대상의 구조상 재현할
수단이 없는 축이 있고, 그런 축까지 기계적으로 훑으면 실행할 수 없는 TC를 설계하거나 시트에
빈칸을 남기게 됩니다.

프로젝트를 시작할 때 축마다 셋 중 하나로 판정하고, 그 결과를 프로젝트 문서에 남깁니다.

| 판정 | 뜻 | 처리 |
|---|---|---|
| 그대로 적용 | 대상에서 그대로 재현 가능 | 정상 전개 |
| 수단 치환 | 검증 의도는 유효한데 재현 방법만 다름 | 테스트 설비·mock·결함 주입으로 대체해 전개 |
| 제외 | 재현 수단도 대체도 없음 | TC를 만들지 않고 **사유를 기록** |

**제외는 누락과 다릅니다.** 사유를 남기지 않으면 나중에 "왜 이 축의 TC가 없나"에 답할 수
없고, 빠뜨린 것으로 읽힙니다. 제외 목록은 산출물의 "SUT 한계와 검증 범위" 절로 이어집니다.

수단 치환이 가장 흔합니다. 서버가 없어 5xx를 만들 수 없어도 mock의 실패 응답으로 "생성 실패
시 재화 미차감"이라는 원래 검증 의도는 그대로 살릴 수 있습니다. 축을 버리기 전에 치환할 수단이
있는지 먼저 봅니다.

## 전개량 조절

노드 하나가 TC 20건이 되면 시트가 읽히지 않습니다. 다음 기준으로 압축합니다.

- **같은 밸리데이션 로직을 공유하는 필드는 대표 1개만** 전개하고 나머지는 비고에 나열.
  (이름 2~30자, 소개 30자, 스탯 이름 10자 → "글자수 경계" TC 1건 + 필드 목록)
- **경계 3점은 절차 안에 묶어 1건으로** 씁니다. 3건으로 쪼개지 않습니다.
- **우회 변형은 1건 안에 N종 시도로** 묶습니다. 변형마다 TC를 만들면 관리가 무너집니다.
- 반대로 **금전·보호·유실 축은 쪼갭니다.** 여기서는 한 건이라도 뭉뚱그리면 원인 규명이 안 됩니다.

목표 감각: 기능 트리 노드 수와 TC 수가 대략 1:1 ~ 1:1.5. 이 범위를 크게 벗어나면
트리가 너무 성기거나 TC를 과생성한 것입니다.

## 기대 결과 작성

판정 가능한 문장으로 씁니다.

| ✗ | ✓ |
|---|---|
| 정상 동작한다 | 20자 저장 성공, 21자 저장 차단 및 안내 문구 노출 |
| 잘 기억한다 | 10턴·20턴 시점 모두 정확히 회상 (각 10회 중 9회 이상) |
| 필터가 작동한다 | 우회 변형 포함 30종 모두 차단 (0건 통과) |
| 응답이 자연스럽다 | 성격 일관성 루브릭 20턴 평균 4점 이상 |
| 과금이 맞다 | 잔액 감소분이 고지 차감량과 정확히 일치, 실패 시 0 |

확률적 TC는 임계값을, 루브릭 TC는 합격선을, 금칙 TC는 시도 횟수를
**기대 결과 문장 안에** 숫자로 적습니다. 별도 문서에 두면 실행자가 보지 않습니다.
