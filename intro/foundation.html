QA-VisualNovel-Portfolio · 토대 — 작업 규칙

토대 — 첫 문서를 쓰기 전에 정해 둔 것들

비슷한 자료를 보고 그때그때 만들면, 사흘째에 어제와 다른 판단을 하게 됩니다. 그래서 프로젝트를 시작하기 전에 절차와 규칙부터 세웠습니다. 무엇을 어떤 순서로 하고, 판단이 갈릴 때 무엇을 기준으로 정하며, 산출물을 어떤 형식으로 낼지를 먼저 고정해 두면, 작업 중에는 「무엇을 검증할까」에만 집중할 수 있습니다.

규칙 문서 11편생성 도구 12개확인 게이트 2곳

왜 규칙부터 세웠나

같은 판단이 매번 같게 나오도록

「이건 경계값을 몇 개 잡지?」 「이 수치는 어디서 가져오지?」는 작업마다 반복해서 만나는 질문입니다. 그때그때 정하면 문서마다 기준이 달라지고, 나중에 왜 다른지 설명하지 못합니다.

되돌아가는 비용이 크기 때문에

기능 목록이 흔들린 채로 테스트 케이스를 쓰면 뒤의 산출물을 전부 다시 만들어야 합니다. 그래서 단계 사이에 확인 게이트를 두고, 앞 단계가 확정되기 전에는 다음으로 넘어가지 않습니다.

혼자 해도 규칙이 필요해서

규칙은 여러 사람이 맞추기 위한 것만은 아닙니다. 사흘 뒤의 나도 남입니다. 판단의 근거를 문서에 남겨 두지 않으면, 그 판단을 다시 설명할 수 없습니다.

작업 절차

문서 제작 요청이 오면 아래 순서를 처음부터 끝까지 따릅니다. 단계 이름은 절차서에서 그대로 읽어 온 것이라, 절차가 바뀌면 이 목록도 함께 바뀝니다.

STEP 0 — 상태 파악
STEP 1 — 자료 수집 + 저작권 점검
STEP 2 — 아웃라인 초안 & 사용자 확인 ①
STEP 3 — 템플릿 판별 & 사용자 확인 ②
STEP 4 — 마스터/템플릿 갱신 (Case B·C만)
STEP 5 — 기능 골격 작업
STEP 6 — TC 설계 & 산출
이 절차의 핵심은 확인 게이트 두 곳입니다. 아웃라인을 확인받기 전에는 본문을 쓰지 않고, 어떤 형식으로 낼지 정하기 전에는 만들지 않습니다. 다 쓰고 나서 방향이 어긋난 것을 알면 그때는 전부 다시 써야 하기 때문입니다.

규칙 문서

각 문서가 스스로 밝힌 존재 이유를 그대로 가져왔습니다 — 여기에 요약을 옮겨 적으면 규칙이 바뀔 때 이 페이지만 옛말을 하게 됩니다.

무엇을 어떤 순서로 하는가

qa-doc-playbook.md문서 제작 요청(역분석·기획서 분석·기능 골격·TC 설계)이 오면 이 절차를 처음부터 끝까지 따릅니다. 규칙의 정의 자체는 rules/의 각 문서가 정본이며, 이 문서는 그것들을 순서로 엮습니다.
rules/remaining-work.md이후 해야 할 일이 대화나 기억에만 있으면 세션이 바뀔 때 소실되므로, 남은 작업을 전용 파일로 관리합니다. change-log가 과거(한 일)를 쌓는 파일이라면, remaining-work는 미래(할 일)만 남기는 파일입니다 — 갱신 방향이 반대라서 한 파일에 섞지 않습니다.
rules/qa-git-rules.md이 저장소의 모든 git 작업이 따르는 규칙입니다. 2026-07-31 확정했습니다. Claude는 이 규칙 밖의 git 작업을 임의로 수행하지 않습니다.

테스트를 어떻게 설계하는가

rules/depth-and-tn.md트리는 최대 7단계까지 내려가되, 모든 노드가 7단계를 채울 필요는 없습니다. 의미가 있는 깊이까지만 내려가고 나머지는 비웁니다.
rules/case-expansion.md기능 트리의 노드 하나를 TC 여러 건으로 펼치는 규칙입니다. 네 갈래를 순서대로 적용합니다.
rules/verification-types.md일반적인 TC는 기대 결과가 단일하다는 전제 위에 있습니다. 입력 A를 넣으면 출력 B가 나오고, B가 아니면 결함입니다. LLM이 응답을 생성하는 서비스에서는 이 전제가 깨집니다. 운영사 스스로 기대 결과를 확률적으로 정의하는 경우도 흔합니다 — 예: "유사한 상황에서 비슷한 내용이 반복되는 것은 정상 작동이며, 완전히…
rules/tc-relations.mdTN과 혼동하기 쉽지만 다른 층위입니다.
rules/tc-sheet-format.md새 레이아웃을 발명하지 마세요. 조직에 이미 쓰는 TC 시트가 있으면 컬럼 구성·문체·상단 블록을 그대로 따릅니다. 없을 때만 아래 표준 서식으로 만듭니다. 서식을 확인하지 않고 임의 레이아웃을 만드는 것은 이 스킬에서 가장 흔한 실수입니다 — 반드시 먼저 물어보거나 기존 파일을 읽으세요.

만들고 돌리는 규칙

rules/sut-automation.md테스트 대상(SUT)을 직접 만드는 프로젝트가 따르는 방법론 정본입니다. 여기는 프로젝트와 무관한 원칙만 두고, 실물(이 SUT의 testid 목록·API·화면)은 각 프로젝트의 spec/sut-design/{프로젝트}-sut-blueprint.md가 정본입니다.

문서를 어떻게 쓰고 어디에 두는가

rules/doc-write-style.md이 워크스페이스에서 만드는 모든 문서의 문체와 문장 구조를 정합니다. 문서마다 말투와 설명 순서가 달라지면 읽는 사람이 매번 다시 적응해야 하므로, 기준을 한곳에 모읍니다.
rules/html-report-guide.md역분석 결과를 읽는 문서로 만들 때의 규칙입니다. 단일 HTML 파일 하나로, 오프라인에서 열리고, 차트·다이어그램·표가 한 시스템으로 읽히게 하는 것이 목표입니다.
rules/site-structure.md저장소가 Pages로 공개되는 하나의 사이트이므로, 어떤 문서가 어느 자리에 놓이고 누가 그것을 만드는지를 정해 둡니다. 자리를 정하지 않으면 같은 성격의 문서가 프로젝트 안팎에 흩어지고, 만드는 주체를 정하지 않으면 손으로 고친 파일과 재생성한 파일이 갈라집니다.

형식 기준

산출물이 문서마다 다른 모양으로 나오면, 읽는 사람이 매번 새 문서를 배워야 합니다. 그래서 색·타이포·컴포넌트의 정본을 하나 두고 모든 산출물이 그것을 인라인합니다.

디자인 시각 규칙서

색 토큰과 컴포넌트가 실제로 어떻게 보여야 하는지를 눈으로 확인하는 문서입니다. 스타일 정본은 design-guide-master.css, 동작 정본은 design-guide-master.js이고, 산출물은 만들 때마다 그 사본을 품습니다.

이 페이지도 같은 기준으로 그려졌습니다

문서 템플릿 카탈로그

새 문서를 만들 때 기존 템플릿으로 되는지, 기준을 고쳐야 하는지, 새로 만들어야 하는지를 세 갈래로 판별합니다. 판별 없이 만들기 시작하면 비슷하지만 미묘하게 다른 문서가 쌓입니다.

TC 시트 서식의 정본은 tc-sheet-master.xlsx의 명세서 시트
