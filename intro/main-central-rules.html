중앙 규칙: 모든 프로젝트가 따라야 하는 규칙

프로젝트를 시작하기 전, 절차와 판단 기준과 형식부터 세웠습니다. 작업을 진행하는 도중 중앙 규칙 단위로 바뀌어야 하는 규칙이 있다면 유저에게 추가·편집할 것인지 제안하고, 유저는 그에 대한 결정을 내립니다. 이를 기반으로 어긋나는 규칙이 있다면 한쪽으로 일치시킴으로써, 프로젝트를 진행할수록 자라는 구조로 설계하였습니다.

규칙 문서 11편생성 도구 13개확인 게이트 2곳

중앙 규칙 워크플로우

중앙 규칙은 모든 작업 앞에 있고, 프로젝트는 그 규칙을 기반으로 삼아 자신만의 프로젝트에 필요한 규칙이나 문서를 추가로 작성해 나갑니다. 아래 그림은 중앙 규칙의 워크플로우를 도식화한 이미지입니다.

왜 중앙 규칙을 분리했나요?

한 프로젝트의 결정이 다른 프로젝트에 유입되지 않도록 사전 차단

규칙을 프로젝트 안에 두고 대화로 키우면, 프로젝트가 늘었을 때 A의 스펙이 B에 섞여 들어옵니다. 규칙을 밖으로 빼면 프로젝트는 서로를 참조할 일이 없어지고, 공유되는 것은 「따라야 하는 기준」뿐입니다.

매번 같은 판단을 참조

규칙이 늘어남에 따라 여러 문서에 담길 수 있는 규칙들의 중복을 제거하고, 하나의 규칙을 기반으로 동일한 판단을 참조할 수 있도록 의도하였습니다.

무엇이 중앙 규칙에 포함되나요?

판별 기준은 「문장에서 프로젝트 이름을 지워도 성립하는가」입니다. 성립하면 중앙 규칙이고, 아니면 프로젝트 규칙 구조입니다.

project-process/ — 절차와 판단 기준

프로젝트의 진행 절차의 규칙을 사전에 정의함으로써, 프로젝트가 늘어도 같은 방식으로 일하도록 유도합니다.

파이프라인 절차서 · 규칙 문서 11편 · 중앙 용어집 · 생성 도구

design-guide/ — 형식의 정본

색·타이포·컴포넌트의 정본이 하나라, 문서마다 스타일을 다시 정하지 않습니다. 산출물은 만들 때마다 그 사본을 품어 네트워크 요청 없이 혼자 열립니다.

시각 규칙서 열기

design-template/ — 새 문서를 만들 때의 틀

새 문서가 기존 템플릿으로 되는지, 기준을 고쳐야 하는지, 새로 만들어야 하는지를 세 갈래로 판별합니다. 문서의 목적과 다른 템플릿을 사용하지 않도록 일관적인 템플릿을 유도합니다.

TC 시트 서식의 정본은 tc-sheet-master.xlsx의 명세서 시트

intro/ — 저장소를 소개하는 층

지금 읽고 계신 문서들입니다. 「프로젝트를 만들기 전에 세운 규칙」처럼 특정 프로젝트 소유가 아닌 이야기가 섞이므로 프로젝트 밖에 둡니다.

전부 생성기가 만드는 파생물입니다

중앙 규칙의 작업 절차

문서 제작 요청이 오면 아래 순서를 처음부터 끝까지 따릅니다. 단계 이름은 절차서에서 그대로 읽어 온 것이라, 절차가 바뀌면 이 목록도 함께 바뀝니다.

STEP 0 — 상태 파악
STEP 1 — 자료 수집 + 저작권 점검
STEP 2 — 아웃라인 초안 & 사용자 확인 ①
STEP 3 — 템플릿 판별 & 사용자 확인 ②
STEP 4 — 마스터/템플릿 갱신 (Case B·C만)
STEP 5 — 기능 골격 작업
STEP 6 — TC 설계 & 산출
이 절차의 핵심은 확인 게이트 두 곳입니다. 아웃라인을 확인받기 전에는 본문을 쓰지 않고, 어떤 형식으로 낼지 정하기 전에는 만들지 않습니다. 다 쓰고 나서 방향이 어긋난 것을 알면 그때는 전부 다시 써야 하기 때문입니다.
규칙을 파악하는 과정에서 중앙 규칙과 다른 상태가 들어오면 그 자리에서 맞추지 않고 유저에게 되묻습니다 — 이 프로젝트의 예외로 둘 것인지, 중앙 규칙을 고칠 것인지. 임의로 한쪽에 맞추면 어느 것이 기준인지 알 수 없게 되고, 다음 프로젝트가 그 상태를 물려받습니다.

규칙 문서

각 문서가 스스로 밝힌 존재 이유를 그대로 가져왔습니다 — 여기에 요약을 옮겨 적으면 규칙이 바뀔 때 이 페이지만 옛말을 하게 됩니다.

무엇을 어떤 순서로 하는가

qa-doc-playbook.md문서 제작 요청(역분석·기획서 분석·기능 골격·TC 설계)이 오면 이 절차를 처음부터 끝까지 따릅니다. 규칙의 정의 자체는 rules/의 각 문서가 정본이며, 이 문서는 그것들을 순서로 엮습니다.
rules/remaining-work.md이후 해야 할 일이 대화나 기억에만 있으면 세션이 바뀔 때 소실되므로, 남은 작업을 전용 파일로 관리합니다. change-log가 과거(한 일)를 쌓는 파일이라면, remaining-work는 미래(할 일)만 남기는 파일입니다 — 갱신 방향이 반대라서 한 파일에 섞지 않습니다.
rules/qa-git-rules.md이 저장소의 모든 git 작업이 따르는 규칙입니다. 2026-07-31 확정했습니다. Claude는 이 규칙 밖의 git 작업을 임의로 수행하지 않습니다.

테스트를 어떻게 설계하는가

rules/depth-and-tn.md테스트 케이스의 뼈대를 이루는 셋을 정합니다 — 기능을 계층으로 정리할 때 어디까지 내려갈지(Depth), 케이스 하나 안에서 동작을 몇 번으로 나눠 적을지(TN), 그리고 무엇부터 확인할지(우선순위)입니다. 이 셋이 흔들리면 같은 기능을 두 사람이 다른 모양으로 적게 되고, 나중에 두 케이스가 같은 것을 보는지조차 알 수 없게 됩니다.
rules/case-expansion.md기능 하나에 케이스 하나만 쓰면 설계대로 되는 경우만 확인하고 끝납니다. 결함은 대개 제한의 언저리나 실패했을 때, 막아 둔 길을 돌아갈 때 나옵니다. 그래서 기능마다 네 갈래로 펼칩니다 — 정상(설계대로 되는가) · 경계(제한의 앞뒤에서 되는가) · 예외(실패·빈 상태에서 되는가) · 우회(막은 길을 돌아갈 수 있는가).
rules/verification-types.md케이스를 쓰기 전에 무엇을 통과라고 부를지부터 정합니다. 값이 하나로 정해지는 항목은 한 번 실행해 맞는지 보면 되지만, AI가 만드는 응답처럼 같은 입력에도 매번 달라지는 항목은 그렇게 자를 수 없습니다. 그래서 항목마다 판정 방식을 넷 중 하나로 먼저 고르고, 그 선택이 몇 번 돌려야 하는지와 어디부터 합격인지까지 함께 정합니다.
rules/tc-relations.md케이스 하나를 실행하려면 먼저 통과해 있어야 하는 다른 케이스가 있습니다. 로그인이 되어야 결제를 볼 수 있는 식입니다. 그 선행 관계를 적어 두어 실행 순서를 정하고, 앞선 케이스가 실패했을 때 뒤따르는 케이스를 어떻게 처리할지도 함께 정합니다. 한 케이스 안의 스텝 순서(TN)와는 다른 층위입니다.
rules/tc-sheet-format.md설계한 테스트 케이스를 실제로 적어 넣는 엑셀 시트의 서식을 정합니다 — 어떤 열을 두고, 한 행에 무엇을 담고, 실행 결과를 어떤 값으로 적을지입니다. 받는 사람이 시트를 읽는 법부터 배우지 않도록 실무에서 쓰는 서식을 그대로 따르고, 규칙만 이 문서로 못박습니다.

만들고 돌리는 규칙

rules/sut-automation.md테스트 대상(SUT)을 직접 만드는 프로젝트가 따르는 방법론 정본입니다. 여기는 프로젝트와 무관한 원칙만 두고, 실물(이 SUT의 testid 목록·API·화면)은 각 프로젝트의 spec/sut-design/{프로젝트}-sut-blueprint.md가 정본입니다.

문서를 어떻게 쓰고 어디에 두는가

rules/doc-write-style.md이 워크스페이스에서 만드는 모든 문서의 문체와 문장 구조를 정합니다. 문서마다 말투와 설명 순서가 달라지면 읽는 사람이 매번 다시 적응해야 하므로, 기준을 한곳에 모읍니다.
rules/html-report-guide.md역분석 결과를 읽는 문서로 만들 때의 규칙입니다. 단일 HTML 파일 하나로, 오프라인에서 열리고, 차트·다이어그램·표가 한 시스템으로 읽히게 하는 것이 목표입니다.
rules/site-structure.md저장소가 Pages로 공개되는 하나의 사이트이므로, 어떤 문서가 어느 자리에 놓이고 누가 그것을 만드는지를 정해 둡니다. 자리를 정하지 않으면 같은 성격의 문서가 프로젝트 안팎에 흩어지고, 만드는 주체를 정하지 않으면 손으로 고친 파일과 재생성한 파일이 갈라집니다.

md 문서와 폴더 링크는 GitHub 저장소에서 열리고, HTML 문서는 이 사이트에서 바로 렌더링됩니다 — GitHub Pages에서는 md가 원본 텍스트로 뜨기 때문입니다.
