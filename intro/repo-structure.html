저장소 구조 — 폴더 이름이 곧 규칙입니다

조사한 것 · 채택한 것 · 확정한 것 · 지나간 것을 한 폴더에 섞어 두면, 테스트의 기대값을 아직 확정되지 않은 값에서 가져오는 사고가 납니다. 그래서 참조 규칙이 같은 것끼리 폴더로 묶고, 폴더 이름만 보고도 「여기 것을 기대값으로 써도 되는가」를 판단할 수 있게 했습니다.

저장소 3층규칙 문서 11편

전체 그림

절차·형식 기준은 모든 작업 앞에 있고, 프로젝트 산출물은 조사에서 확정으로 좁혀지며, 확정된 것에서만 테스트가 나옵니다. 아래 그림의 정본은 저장소 루트의 structure.svg 파일 하나이고, 이 페이지는 그 파일을 그대로 읽어 넣습니다.

세 층으로 나눠 둔 이유

① 절차 — project-process/

무엇을 어떤 순서로 할지, 판단이 갈릴 때 무엇을 기준으로 정할지를 담습니다. 프로젝트가 생기기 전에 세운 층이라, 프로젝트가 늘어도 같은 방식으로 일하게 됩니다.

파이프라인 절차서 · 규칙 문서 · 생성 도구

② 형식 — design-guide/ · design-template/

모든 산출물이 같은 모양으로 나오게 하는 층입니다. 색과 컴포넌트의 정본이 하나라, 문서마다 스타일을 다시 정하지 않습니다.

스타일 정본 · 시각 규칙서 · 문서 템플릿 · TC 시트 서식

③ 산출물 — projects/{프로젝트}/

실제 작업이 쌓이는 층입니다. 안에서 다시 조사 → 채택 → 확정으로 좁혀지고, 확정된 것에서만 테스트 케이스가 나옵니다.

현재 프로젝트 1개 · 기능 86개 · TC 153건

폴더마다 다른 참조 규칙

같은 프로젝트 안이라도 폴더에 따라 「기대값으로 써도 되는가」가 다릅니다. 이 구분이 이 저장소에서 가장 중요한 규칙입니다.

폴더무엇이 있나기대값으로 쓸 수 있나
analysis/출시 서비스를 조사한 전량. 버리지 않고 모읍니다안 됩니다 — 남의 서비스 값입니다
reference/조사분 중 「이건 가져오자」고 고른 것안 됩니다 — 아직 확정 전입니다
spec/ (평면)기능 목록 정본. 손으로 고치는 유일한 파일됩니다
spec/design/확정 사양 — 상한값·차감량·임계·합격선됩니다 — 수치의 출처입니다
spec/sut-design/검증 대상 전용 사양 — 청사진·저장 스키마·고장 주입구현·자동화만 — 기획 테스트는 참조하지 않습니다
spec/rationale/왜 그렇게 정했는지의 기록안 됩니다 — 판단 기록이지 확정안이 아닙니다
spec/archive/지나간 것 — 이력과 동결본안 됩니다 — 평상시에는 열지도 않습니다
test-case/테스트 케이스 설계 원본(json)과 시트(xlsx)설계 결과입니다
sut/검증 대상 그 자체테스트가 조작하는 쪽입니다
automation/테스트 코드 · 실행 결과 · 리포트실행 결과입니다
지나간 것을 archive/로 몰아 두는 이유는 단순합니다 — 삭제된 옛 기능 정보가 평상시 작업에 섞이면, 있지도 않은 기능의 테스트를 쓰게 됩니다. 그래서 기능 목록 정본에는 현재 상태만 남기고 삭제 흔적을 두지 않습니다.
