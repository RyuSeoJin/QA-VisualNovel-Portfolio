## 프로젝트 정의

출시된 서비스를 역분석해 공통 기능을 뽑고, 그 기능으로 **테스트 대상(SUT)인 HTML 미연시를 직접 만들어
자동화 테스트까지 돌리는** 포트폴리오입니다. 역분석 대상과 테스트 대상이 다른 프로젝트입니다.

목표 기간은 3일입니다. 지원 맥락은 AI 채팅·미연시·여성향 앱 회사의 QA이며, 그 회사는 아직 개발
단계(미출시)입니다. 그래서 라이브 운영 QA보다 **명세가 없는 상태에서 골격을 세우는 능력**과
**LLM 출력에 합격선을 긋는 능력**이 평가 대상입니다.

**조사 형식(2026-08-01 사용자 지시)**: 레퍼런스마다 **처음 켰을 때부터 유저가 할 수 있는 행동을 전부** 여정 순서로 정리합니다. 기능 목록이 아니라 행동 인벤토리가 조사의 1차 산출물이고, 공통 트리 컬럼은 거기서 뽑습니다.

오토·스킵, 분기와 호감도, 엔딩·CG 갤러리, 스틸 회수율.

## 확정된 결정

### 폴더 체계 (규칙 정의 완료 — `ef12178`)

폴더 자체는 첫 산출물과 함께 만들어집니다. git이 빈 폴더를 담지 못하므로 현재 실재하는 것은
`analysis/` 하나입니다.

```
projects/visualnovel-qa-lab/
├─ analysis/        조사 전량 — 버리지 않고 모음
├─ reference/       채택분 — 쓰기로 고른 것들의 구체 사양
├─ spec/            확정 결정 — 정본이 사는 곳. TC 기대값은 여기서만
│   ├─ rationale/   근거 — 참조 자유
│   └─ archive/     골격 이력 + 동결 스냅샷 — 기본 참조 금지
├─ test-case/       설계 원본 json + 설계 시트 xlsx
│   └─ archive/     기본 참조 금지
├─ sut/             테스트 대상 (HTML 미연시)
└─ automation/
    ├─ tests/       테스트 코드
    ├─ report/      리포트 HTML (Pages 공개)
    └─ result/      결과 시트
        └─ history/   지난 결과 — 열람 자유
```

`archive/`와 `result/history/`의 규칙이 **정반대**입니다. 앞은 폐기된 것이라 격리하고, 뒤는
회귀 비교용이라 자유롭게 봅니다.

### 정본과 파일 지위

| 파일 | 성격 | 커밋 |
|---|---|---|
| `spec/…-feature-tree.md` | **골격 정본** — 손으로 고치는 유일한 파일 | 필수 |
| `spec/rationale/…-addition-rationale.md` | **판단 기록** — 조사로 방어되지 않는 부분의 근거 | 필수 |
| `spec/archive/…-tree-change-log.md` | 골격 변경 이력 | 필수 (기본 참조 금지) |
| `nodes.json` | 순수 중간물 — 명령 한 줄로 재생성, 결과 항상 같음 | **불필요** (`.gitignore`) |
| `test-case/…-tc-input-v{X.Y}.json` | **TC 설계 원본** — 케이스 전개라는 사람의 판단이 들어감 | 필수 |
| `test-case/…-tc-v{X.Y}.xlsx` | 파생 (배포물) | 필수 |
| `automation/report/`, `result/` | 파생 (대표 1부만) | 필수 |

정본에 **`REF`/`ADD` 컬럼**을 둡니다. `REF`는 레퍼런스에서 채택한 것, `ADD`는 레퍼런스에 없어
직접 정한 보강분입니다. 근거는 `spec/rationale/visualnovel-qa-lab-addition-rationale.md`에 모으고,
노드를 세운 근거(**§1 노드 보강**)와 값이 공개되지 않아 직접 정한 수치의 근거(**§2 수치 확정**)를
섹션으로 나눕니다. 면접에서 가장 많이 받을 질문이 "그 숫자는 왜 그렇게 정했나요?"이므로 §2를 함께
모읍니다.

**`spec/` 평면에는 확정안만 둡니다** (2026-07-31 변경 — 하위 폴더 없는 평면 구조에서 참조 규칙별
분리로). 파일마다 열어도 되는지를 외우면 실수로 옛 정보를 끌어오게 되므로, 근거는 `rationale/`,
지나간 상태는 `archive/`로 갈라 폴더 이름이 곧 참조 규칙이 되게 했습니다. `history/`라는 이름은
쓰지 않습니다 — `automation/result/history/`가 열람 자유를 뜻해 같은 이름이 상반된 규칙을 갖게
됩니다.

### SUT 설계

SUT는 문서가 아니라 프로그램이므로 자기완결 단일 파일 규칙의 예외입니다. 처음부터 테스트가
붙잡을 손잡이를 심어 만듭니다.

| 손잡이 | 내용 |
|---|---|
| `data-testid` | TC ID와 연결. 클래스·화면 문구로 요소를 찾지 않습니다 |
| `window.__VN__` | `getState()` · `getSave(slot)` · `reset()`. 화면에 안 보이는 값을 읽는 통로 |
| `?seed=42` | mock LLM 응답 선택 고정. 실패 시 같은 조건으로 재현 |
| `?inject=…` | 결함 주입 — `persona-drift` · `save-leak` · `ghost-memory` · `gate-bypass` |

**상태 조회 훅이 격리 계열 금칙 TC를 실행 가능하게 만드는 유일한 통로**입니다. 세이브 슬롯 간
오염은 화면만 봐서는 검증되지 않습니다.

### 자동화 설계

- **Playwright for Python**(`pytest-playwright`) 우선. Python 3.14에서 휠이 없으면 Node LTS로 전환
- **케이스명 = TC ID** — `test_tc_nar_003_호감도_가산`. 리포트만 보고 시트와 대조됩니다
- 반복은 **테스트 함수 안에서** 돌립니다. `parametrize`로 쪼개면 성공률 계산이 안 됩니다
- 반복 횟수·임계값은 `thresholds.py` 한 곳에 모읍니다. 리포트가 그 값을 읽어 찍습니다
- 파일은 기능 트리 1-Depth 영역 단위로 나눕니다 — `test_narrative.py`, `test_safety.py` 등
- `conftest.py`에서 **매 테스트 전 `__VN__.reset()`**. 앞 테스트의 세이브가 남으면 격리 검증이 무의미해집니다
- 루브릭은 자동화하지 않습니다. 채점 결과를 `rubric-scores.csv`로 남기고 리포트가 읽어갑니다
- 자동화는 xlsx가 아니라 `…-tc-input.json`을 읽습니다 — 커버리지 대조, 검증유형별 반복 횟수 결정

### CI (GitHub Actions)

- **`deploy-pages` 액션을 쓰지 않습니다.** Pages 배포 방식을 브랜치 배포에서 Actions 배포로
  바꾸면 기존 사이트가 내려갑니다. 리포트는 저장소에 커밋해 Pages가 서빙하게 합니다
- 리포트는 `upload-artifact`로도 남깁니다(기본 90일 후 만료). CI 실행분을 전부 커밋하면
  이력이 결과 파일로 도배됩니다
- 경로 필터로 필요할 때만 돌립니다 — `sut/**`, `automation/**`, `*-tc-input*.json`
- **결함 주입 매트릭스를 CI에 묶습니다.** 행=주입한 결함, 열=TC, 대각선에만 FAIL이 떠야 정상입니다.
  대각선이 PASS면 그 TC가 부실한 것입니다

### 검증유형 4종의 실제 검증 범위

`rules/verification-types.md`의 4종을 SUT에 배분하되, **SUT가 mock이라는 한계를 문서에 명시합니다.**

| 유형 | SUT에서 | 비고 |
|---|---|---|
| 결정적 | **완전 검증** | 호감도 가감산, 엔딩 경계값, 세이브 정합, 재화 차감 |
| 금칙 — 격리 계열 | **완전 검증** | 세이브 간 오염, 삭제 메모리 재등장. 상용 서비스와 결함 메커니즘 동일 |
| 금칙 — 안전 계열 | 부분 | 게이팅·필터 계층은 검증됨. **모델 자체의 안전성은 검증 불가** |
| 확률적 | 계측만 | 변주 폭을 직접 작성했으므로 수치는 품질 지표가 아님 |
| 루브릭 | 계측만 | 같은 이유. 루브릭 정의서·채점 시트·턴수별 곡선이 산출물 |

분석 문서 말미에 **"SUT 한계와 검증 범위"** 섹션을 반 페이지로 넣습니다. 이 섹션이 없으면
"mock인데 준수율 92%가 무슨 의미죠?"라는 질문에 무너집니다.

**포트폴리오의 값어치는 미연시의 완성도가 아니라 QA 판단의 증거입니다.** SUT는 작품이 아니라
테스트 대상이므로, 미술·스토리 분량은 최소로 갑니다. 일정이 무너지는 지점은 언제나
"SUT 꾸미기"입니다.

### 시간 도둑 네 가지

1. **SUT 꾸미기** — 최대 위험. 기능 트리 노드 구현 외의 작업은 하지 않습니다

3. **레퍼런스 조사 과다** — 오전 반나절로 제한. 게이트 안쪽은 `?`로 남깁니다
4. **자동화 전량 시도** — 회귀 핵심만. 안 한 이유를 문서화하는 쪽이 점수가 큽니다

1. 자동화 리포트 전용 템플릿(Case C) → 기본 리포트 사용

4. 확률적 케이스 수 축소

**절대 버리지 않는 것** — 결정적·금칙 격리 계열 자동화, 추적 매트릭스(기능트리 → TC → 자동화),
"SUT 한계와 검증 범위" 섹션. 이 셋이 포트폴리오의 뼈대입니다.
