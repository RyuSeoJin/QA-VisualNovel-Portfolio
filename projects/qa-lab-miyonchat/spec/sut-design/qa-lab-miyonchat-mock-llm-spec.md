# qa-lab-miyonchat — mock LLM 사양 (mock-llm-spec)

## 0. 문서 지위

- ②SUT 레이어 사양입니다. 실제 LLM 없이 **시드로 결정되는 응답 세트**의 구조 정본이며,
  `?seed={n}` 파라미터의 의미를 정의합니다
- 호감도 임계·엔딩 판정식 등 기획 값은 `design/…-system-spec.md`가 정본입니다

## 1. 결정성 원칙

- **같은 시드 + 같은 입력 순서 = 항상 같은 응답열**입니다. 실패한 테스트는 시드와 입력을
  기록하는 것만으로 재현됩니다
- 시드 미지정 시 기본값은 `seed=1`입니다
- 무작위 함수를 쓰지 않습니다 — "변주"조차 시드가 고르는 결정적 분기입니다

## 2. 응답 세트 구조

캐릭터×시작 상황마다 턴 순서대로 응답 후보를 정의하고, 시드가 후보 중 하나를 고릅니다.
**시작 상황은 캐릭터당 하나이고 유저가 고르지 않습니다**(system-spec §8-8) — `scenarioId`는
경로 좌표로 남겨 두어, 나중에 한 캐릭터에 경로가 늘어도 구조를 바꾸지 않게 합니다.

```json
{
  "characterId": "c1",
  "scenarioId": "s1",
  "turns": [
    {
      "turn": 1,
      "candidates": [
        {
          "kind": "message | direction",
          "text": "…{userName}… {nickname}…",
          "deltaAffection": 1,
          "memoryAdd": "민트초코를 싫어함",
          "memoryRefs": ["mem1"],
          "personaReflect": true,
          "contextReflect": true,
          "blockedToken": false,
          "fail": false
        }
      ],
      "choices": [
        { "label": "…", "delta": 2 },
        { "label": "…", "delta": 1 },
        { "label": "…", "delta": -1 }
      ]
    }
  ],
  "endTurn": 24
}
```

| 필드 | 규칙 |
|---|---|
| `candidates` | 시드 mod 후보 수로 선택 — 후보마다 반영/미반영·델타가 다를 수 있음 |
| 재생성 시 후보 | **한 칸 밀어 고릅니다**(마지막 후보 다음은 처음으로 돌아옵니다). 난수를 쓰지 않으므로 "몇 번째 재생성인가"가 정해지면 어떤 응답이 나오는지도 정해집니다 — 되돌림 검증이 기대값을 적을 수 있는 근거입니다(system-spec §5-1) |
| `text`의 `{userName}`·`{nickname}` | 페르소나 삽입 슬롯 — 준수율 검증이 붙잡는 지점 |
| `personaReflect` / `contextReflect` | 이 후보가 페르소나/단기 맥락을 반영하는 변주인지 표기 — 계측 TC가 분포를 읽는 근거 |
| `memoryAdd` | 유저에 대해 알게 된 것 `{ id, text, brief }`. **그 턴의 모든 후보에 같은 값으로 답니다** — 시드가 어느 후보를 고르든 같은 턴에 같은 기억이 쌓여야 시드와 무관한 규칙이 됩니다. 장면이 끝나면 `text` 대신 `brief`가 남습니다(system-spec §7-1) |
| `memoryRefs` | 그 기억을 언급하는 응답. **한 턴에 하나의 후보에만 답니다** — 모든 후보가 참조를 달면 기억을 지웠을 때 넘어갈 자리가 없어 차단이 성립하지 않습니다. 기본 시드가 고르는 자리에 두어, 평소에는 참조 응답이 나오고 기억이 없으면 참조 없는 후보로 넘어갑니다 |
| `events` | 장면 구간 `{ id, label, from, to }`. **끝나는 턴을 지나면 그 구간의 기억이 간략화**됩니다. 10턴 안팎으로 잘게 잡습니다 — 서사의 하루를 그대로 쓰면 첫 간략화까지 33턴을 진행해야 해서 사람이 손으로 확인하기 어렵습니다 |
| `choices` | 고정 선택지와 가중치(+2/+1/−1) — 없는 턴은 자유 입력만 |
| `fail: true` | 생성 실패 재현 후보. **기본 세트에는 두지 않습니다** — 서버 오류는 정상 플레이에서 저절로 나는 사건이 아니라 테스트가 일으키는 조건이기 때문입니다. 사람은 T1 스위치로, 자동화는 `__VN__.failNext()`로 일으킵니다(둘 다 1회성). **실패는 아무것도 소비하지 않습니다** — 잔액·내역·턴수·대화수·메시지 어디에도 흔적이 남지 않고 토스트로만 알립니다 |
| `blockedToken: true` | 출력 필터 검증용 — 응답에 추상 금칙 토큰 포함 |
| `endTurn` | 경로 종점 — 도달 시 엔딩 최종 판정(system-spec §4-2) 트리거 |

### 2-1. 세트 범위 (2026-08-02 확정)

캐릭터마다 전용 대사를 깔면 분량만 늘고 검증에 보태는 것이 없으므로, 세트를 둘로 나눕니다.

| 세트 | 대상 | 쓰임 |
|---|---|---|
| **전용 세트** | **사흘의 바다(c7) — 100턴** | 서사 진행·검사 시점(19회)·엔딩 도달·맥락 창을 보는 기준 경로. TC의 기본 경로는 여기를 씁니다 |
| **공통 세트** | 그 외 전 캐릭터 + T1에서 생성한 캐릭터 — **30턴** | 캐릭터 이름·호칭만 치환되는 중립 대사. 방 격리·계정 격리·재화·되돌림처럼 **대사 내용과 무관한 규칙**은 이 세트로 검증합니다 |

- 전용 세트가 없는 캐릭터는 **자동으로 공통 세트**를 씁니다 — 시트에 캐릭터를 새로 만들어도
  대화가 성립해야 목록 증가와 대화 진입을 한 흐름으로 검증할 수 있기 때문입니다
- 어느 세트를 쓰는지는 **T1 캐릭터 표에 표시**합니다. 화면에서 읽히지 않으면 "왜 이 캐릭터는
  대사가 다른가"를 결함으로 오인하게 됩니다

### 2-2. 긴 경로는 조립으로 만듭니다

100턴·30턴 분량의 대사를 한 줄씩 적으면 파일이 검증과 무관한 분량으로 불어납니다. 서사를
구간으로 나누고 **구간별 대사 풀에서 턴 번호로 뽑아 조립**합니다.

- 난수를 쓰지 않으므로 **같은 턴이면 언제나 같은 후보**가 나옵니다 — 결정성은 그대로입니다
- 구간 안에서 대사가 순환하므로 긴 대화에서는 같은 문장이 다시 보입니다. 검증 대상은 대사
  내용이 아니라 상태 규칙이므로 그대로 둡니다
- 전용 세트 구간: 1~33턴 첫날 · 34~66턴 둘째 날 · 67~100턴 마지막 날. 3턴마다 고정 선택지
- 서사의 하루 안에 **장면(이벤트)을 10턴 안팎으로 잘게** 둡니다 — 첫 만남·해질녘·첫날 밤 …
  장면마다 기억이 하나 쌓이고, 몇 턴 뒤 그 기억을 언급하는 응답이 옵니다. 그래서 한 장면
  안에서 「쌓임 → 언급 → 장면 종료로 간략화」가 모두 지나갑니다

## 3. 변주 분포 (계측의 전제)

- 계측용 변주(페르소나·맥락 반영 여부)는 시드 후보 배치로 만들며, 설계 분포는 **반영 후보
  80% 이상**을 기본으로 합니다 — 합격선 80%와 짝입니다
- 이 분포를 우리가 작성했으므로 **계측 수치는 품질 지표가 아닙니다.** 이 문장은 리포트와
  분석 문서에 그대로 들어갑니다

## 4. 스트리밍·삭제 연동

- 응답은 문자 단위 타이핑 연출로 표시되고, 표시 완료 이벤트 후 상태 델타가 반영됩니다 —
  검증은 "표시 완료"만 봅니다(연출 시간은 검증 대상 아님)
- 삭제·재생성으로 버려진 메시지는 이후 턴의 맥락 계산(`memoryRefs`·`contextReflect`)에서
  제외됩니다 — 되돌림 공통 원칙(system-spec §5-1)의 mock 측 이행입니다
