## 프로젝트 정의

출시된 서비스를 역분석해 공통 기능을 뽑고, 그 기능으로 **테스트 대상(SUT)인 HTML 미연시를 직접 만들어
자동화 테스트까지 돌리는** 포트폴리오입니다. 역분석 대상과 테스트 대상이 다른 프로젝트입니다.

목표 기간은 3일입니다. 지원 맥락은 AI 채팅·미연시·여성향 앱 회사의 QA이며, 그 회사는 아직 개발
단계(미출시)입니다. 그래서 라이브 운영 QA보다 **명세가 없는 상태에서 골격을 세우는 능력**과
**LLM 출력에 합격선을 긋는 능력**이 평가 대상입니다.

**조사 형식(2026-08-01 사용자 지시)**: 레퍼런스마다 **처음 켰을 때부터 유저가 할 수 있는 행동을 전부** 여정 순서로 정리합니다. 기능 목록이 아니라 행동 인벤토리가 조사의 1차 산출물이고, 공통 트리 컬럼은 거기서 뽑습니다.

오토·스킵, 분기와 호감도, 엔딩·CG 갤러리, 스틸 회수율.

### SUT 설계

SUT는 문서가 아니라 프로그램이므로 자기완결 단일 파일 규칙의 예외입니다. 처음부터 **SUT
테스트 인터페이스**(SUT가 테스트 코드에 열어주는 접점 — 구 표현 "손잡이", 2026-08-01 용어
확정)를 심어 만듭니다. 구조 정본은 `spec/sut-design/…-sut-blueprint.md` §3입니다.

| 인터페이스 | 내용 |
|---|---|
| `data-testid` | TC ID와 연결. 클래스·화면 문구로 요소를 찾지 않습니다 |
| `window.__VN__` | `getState()` · `getSave(slot)` · `reset()`. 화면에 안 보이는 값을 읽는 통로 |
| `?seed=42` | mock LLM 응답 선택 고정. 실패 시 같은 조건으로 재현 |
| `?inject=…` | 결함 주입 — `persona-drift` · `save-leak` · `ghost-memory` · `gate-bypass` |

**상태 조회 훅이 격리 계열 금칙 TC를 실행 가능하게 만드는 유일한 통로**입니다. 세이브 슬롯 간
오염은 화면만 봐서는 검증되지 않습니다.

### 자동화 설계

- **Playwright for Python**(`pytest-playwright`) 우선. Python 3.14에서 휠이 없으면 Node LTS로 전환
- **케이스명 = TC ID** — `test_tc_nar_003_호감도_가산`. 리포트만 보고 시트와 대조됩니다
- 반복은 **테스트 함수 안에서** 돌립니다. `parametrize`로 쪼개면 성공률 계산이 안 됩니다
- 반복 횟수·임계값은 `thresholds.py` 한 곳에 모읍니다. 리포트가 그 값을 읽어 찍습니다
- 파일은 기능 트리 1-Depth 영역 단위로 나눕니다 — `test_narrative.py`, `test_safety.py` 등
- `conftest.py`에서 **매 테스트 전 `__VN__.reset()`**. 앞 테스트의 세이브가 남으면 격리 검증이 무의미해집니다
- 루브릭은 자동화하지 않습니다. 채점 결과를 `rubric-scores.csv`로 남기고 리포트가 읽어갑니다
- 자동화는 xlsx가 아니라 `…-tc-input.json`을 읽습니다 — 커버리지 대조, 검증유형별 반복 횟수 결정

### CI (GitHub Actions)

- **`deploy-pages` 액션을 쓰지 않습니다.** Pages 배포 방식을 브랜치 배포에서 Actions 배포로
  바꾸면 기존 사이트가 내려갑니다. 리포트는 저장소에 커밋해 Pages가 서빙하게 합니다
- 리포트는 `upload-artifact`로도 남깁니다(기본 90일 후 만료). CI 실행분을 전부 커밋하면
  이력이 결과 파일로 도배됩니다
- 경로 필터로 필요할 때만 돌립니다 — `sut/**`, `automation/**`, `*-tc-input*.json`
- **결함 주입 매트릭스를 CI에 묶습니다.** 행=주입한 결함, 열=TC, 대각선에만 FAIL이 떠야 정상입니다.
  대각선이 PASS면 그 TC가 부실한 것입니다

### TN은 연쇄에만 쓴다 — 나열은 케이스로 (2026-08-03)

첫 영역을 써 보인 뒤 사용자가 짚었습니다. TN은 **앞 스텝의 결과로 뜬 UI**(팝업·다이얼로그처럼
별도 Depth로 두기 애매한 것)를 확인하려고 번호를 올리는 장치인데, 제가 **대상만 바꿔 같은 검증을
되풀이하는 나열**을 TN으로 늘어놓았습니다. 규칙 문서에도 「1번 이후에 **이어지는** 동작」이라고
적혀 있었으나 나열로 읽었습니다.

- 판정 기준을 규칙에 세웠습니다 — **스텝 하나를 떼어 내도 나머지가 그대로 수행되면 나열**이고,
  케이스를 나눕니다. 연쇄는 앞 스텝을 빼면 다음 스텝을 수행할 수 없습니다
  (`rules/depth-and-tn.md` §TN으로 이을 수 있는 것은 연쇄뿐입니다)
- §케이스를 쪼개는 기준의 맨 앞에 **⓪ 연쇄 여부**를 넣었습니다. 나열이면 나머지 기준을 따질
  것도 없이 나눕니다
- 나열을 TN으로 묶으면 Total Result가 한 덩어리가 되어, 대상 하나만 깨져도 케이스 전체가
  Fail이고 **어느 대상이 깨졌는지 TC ID로 읽히지 않습니다**
- 적용 결과 「웹 진입」이 8건에서 **11건**이 되었습니다. 보호 화면 셋(채팅 탭·MY 탭·내 작품 탭)과
  공개 화면 둘(홈 화면·커뮤니티 탭)이 각자 케이스를 가집니다

### 케이스를 쪼개는 기준 신설 (2026-08-03)

첫 케이스를 쓰다 「만료 후 재진입」과 「만료 상태에서 보호 동작 차단」을 한 케이스에 담을지가
걸렸습니다. 판단이 그때그때 달라지면 영역마다 케이스 크기가 들쭉날쭉해지므로 기준을 세워
`rules/depth-and-tn.md` §케이스를 쪼개는 기준으로 두었습니다.

- **스텝이 여럿이라는 이유만으로는 쪼개지 않습니다.** 검증유형이 갈릴 때 · 앞은 정상인데 뒤만
  실패한 것을 남겨야 할 때 · 앞이 실패하면 뒤를 확인조차 할 수 없을 때 셋만 가릅니다
- 가장 큰 이유는 **검증유형이 케이스 단위 값**이라는 점입니다. 진입 확인(결정적)과 차단
  확인(금칙)이 한 케이스에 있으면 한 값을 공유해야 하는데, 금칙은 사실상 전부 High이고 집계도
  따로 보는 축이라 섞이면 둘 다 변별력을 잃습니다
- 쪼갠 뒤에는 **선행 TC로 다시 잇고 사전조건을 앞 케이스가 끝난 상태로** 적습니다. 뒤 케이스만
  따로 실행해도 시작점이 서고, 앞이 Fail일 때 Blocked 판정의 근거가 생깁니다
- 적용 결과 TC-ENT-003(만료 후 재진입·결정적)과 TC-ENT-004(만료 상태 보호 동작 차단·금칙)로
  갈랐습니다. 행 모양과 판정 수는 그대로이고 TC ID·TN만 바뀝니다

### 기대결과 입력을 스텝별 배열로 (2026-08-03)

규칙은 이미 「한 스텝에 기대결과가 여럿이면 행을 늘리고 TN·Test-Step을 병합한다 — **어느
스텝에서든**」이었는데(`depth-and-tn.md`), **생성기가 그렇게 동작하지 않았습니다.** 입력의
기대결과가 문장을 이어 쓴 문자열 하나라 어느 판정이 어느 스텝의 것인지 담을 자리가 없었고,
생성기는 개수가 같을 때만 순서로 짝짓고 다르면 전부 마지막 스텝에 실었습니다. 그 결과 앞
스텝의 기대결과 칸이 비어 **어느 동작의 판정인지 시트에서 읽히지 않았습니다.**

- 입력에서 기대결과를 **스텝별 배열**로 받게 했습니다. 소속을 입력이 직접 말하므로 중간
  스텝에서도 판정을 여럿 달 수 있고, 병합·집계는 스텝 블록 기준이라 그대로 동작합니다
- 문자열 형식도 계속 읽습니다 — 옛 입력 호환용이며 새 케이스는 배열로 씁니다
- 규칙 변경이 아니라 **생성기를 규칙에 맞춘 것**입니다

### 영역코드 매핑 신설 (2026-08-03)

TC ID의 형식은 정해져 있었지만(`TC-{영역코드}-{번호}`) **실제 매핑표가 어디에도 없었습니다** —
생성 스크립트의 명세서가 「매핑표는 프로젝트에서 정의합니다」라고 가리키기만 했습니다. 첫 케이스를
쓰려면 코드가 필요하므로 열 개를 정하고 정본 자리를 만들었습니다.

- 정본은 `tc-input` json의 `area_codes`이며 **키는 기능 트리 1-Depth 영역명**입니다. 이슈 관리
  시트 「레이블」 목록과 같은 값이라야 영역별 이슈 집계가 TC 영역과 대응됩니다
- 항목마다 **영문 표기를 함께 담습니다.** 코드만 남기면 나중에 읽는 사람이 무엇의 약자인지
  복원할 수 없기 때문이며, 코드는 그 영문 표기의 앞 세 글자입니다
- 생성기가 이 값을 **명세서 시트 §5-1로 렌더**합니다. 시트만 받은 사람도 표에서 읽을 수 있어야
  하므로 입력 파일에만 두지 않습니다. 정의가 없는 프로젝트에서는 그 절이 생략됩니다
- 코드: ENT(앱 진입/세션) · GAT(계정/게이팅) · DSC(탐색/발견) · PRF(유저 페르소나) ·
  CUR(재화) · NAR(서사 시스템) · CHT(대화 세션) · SAV(세이브/로드) · MEM(메모리/컨텍스트) ·
  SAF(입력/출력 세이프티)

### RC21 — 확정 값을 코드가 따라감 (2026-08-03)

기획에서 먼저 정한 §8-8 두 값을 SUT가 구현했습니다. 확인은 실제 화면으로 했습니다 — 버전이
`1.2` 저장값에서 `(v1.2)`로 그려지고, c1의 추천이 좋아요 내림차순으로 카일(640)·은결(400)이며,
좋아요를 임계 아래로 내리면 빠지고, 상한을 1로 내리면 하나만 남고, 임계를 올려 후보를 없애면
「관련 추천 작품이 없습니다」가 뜨며, 세이프티 필터를 켜면 언세이프인 카일이 후보에서 빠집니다.

- **버전 저장 형식을 숫자로 바꿨습니다** — 명세가 「표시할 때 `v`를 붙인다」이므로 저장에 접두를
  담으면 같은 사실이 두 곳에 생깁니다. 데이터의 `v1.2`를 `1.2`로 고치고 표시에서 붙입니다.
  입력은 숫자와 점만 받아 `v`를 직접 적어도 걸러집니다
- **추천의 임계·정렬 판정에 `likeCount`를 씁니다** — 화면에 보이는 좋아요 수(시트 값 + 내가 누른
  것)와 판정 근거가 갈라지면 「10인데 왜 빠졌나」를 설명할 수 없습니다. §8-4 체인이 이미 같은
  값을 쓰므로 목록 규칙이 하나로 유지됩니다
- **후보 0건이면 섹션을 감추지 않고 안내를 남깁니다** — 감추면 「안 뜬 것」과 「없는 것」이
  구분되지 않습니다. 기본 데이터에서 자주 나오는 화면이라 `s3-related-empty`를 새로 붙였습니다

### 결정 대기 항목 정리 (2026-08-03 확정)

TC 본문에 착수하기 전에 열려 있던 결정을 닫았습니다.

- **이슈와 TC의 연결** — 연결의 정본을 `issues.json`의 **「발견 기록」 배열**로 옮겼습니다.
  원소는 `{TC ID, 확인버전}` 한 쌍이고, Test Case 시트의 `Issue No.`는 **TC ID와 확인버전 둘로
  조인**해 그 회차에 발견된 것만 채웁니다. 예전 회차의 이슈가 딸려 들어오면 이번에는 통과했는데
  실패한 것처럼 보이기 때문입니다. 배열은 덧붙이기만 하므로 첫 원소가 최초 발견을 뜻하고,
  「최초 발견 회차」는 따로 저장하지 않고 계산해 표시합니다. 규칙 정본은
  `rules/tc-sheet-format.md` §이슈 관리 시트
- **트리 미확인 2건 해소** — 업데이트 버전 표기 형식과 그 외 작품 추천 선정식을 확정해
  `design/…-system-spec.md` §8-8로 옮기고 골격을 v1.10으로 올렸습니다. 값을 SUT 코드에서 읽어
  오지 않고 기획에서 먼저 정했습니다 — SUT는 기획을 구현하는 쪽이라 반대로 하면 임시 구현이
  확정으로 승격됩니다
- **트리의 조사 후보 수치 제거** — 「호감도 증감」 설명에 남아 있던 `후보 +1/+2/−1`을 지웠습니다.
  확정값 `+2 / +1 / −1`과 세 숫자가 같은데 순서가 달라 배정을 거꾸로 읽을 여지가 있었습니다
- **`build_tc_xlsx.py` 삭제** — 분석 문서를 HTML로 내기로 해 tree·risks 시트가 갈 곳을 잃었고,
  `tcs` 스키마가 옛 13필드라 잘못된 형식의 근거로 읽힐 위험이 있었습니다. 저장소 전체에서
  참조가 없음을 확인한 뒤 지웠습니다
